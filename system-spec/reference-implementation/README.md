# Reference Implementation

Validates [spec.md](../spec.md) with Python, Pydantic, YAML, and pytest.

- Validate spec: `uv run python metamodel.py example.yaml [--stage inventory|discovery|architecture|verification|release]` (default `release`)
- Export schema: `uv run python metamodel.py --schema > schema.json` (committed; regenerate on model change, a test checks drift). Specs reference it via a `# yaml-language-server: $schema=…` modeline.
- Impact analysis: `uv run python metamodel.py example.yaml --impact order` (`--impact` and `--plan` also accept an imported capability `<import>:<capability>`, seeded with the components that `requires` or `test_requires` it); `--impact-paths PATH…` (or `-` for paths on stdin, e.g. `git diff --name-only`) maps changed files to components by `source_paths`/`test_paths` (longest match) and prints the union impact plus `tests` (the `test_paths` entries and selectors of affected components and dependents), `changed_components` and `unmapped_paths`
- Compatibility: `uv run python metamodel.py new.yaml --compat old.yaml`
- Context slice: `uv run python metamodel.py example.yaml --context checkout`
- Split specs: a root spec keeps `system` (plus `capabilities: []` and `components: []`) and lists `include: [spec/*.yaml]`; fragments hold any other section (schema: `fragment.schema.json`, `--fragment-schema`), are merged in sorted order, and the result is validated as one spec. Errors cite the fragment file. See `examples/components/`.
- Diagram: `uv run python metamodel.py example.yaml --diagram [components|hierarchy|risks|runtime]` — Mermaid flowchart (`components`, `runtime` top-to-bottom; `hierarchy`, `risks` left-to-right); kinds and default: [README § Common commands](../README.md#common-commands). `components` (default): layers, nested domains, resolved capability dependencies, data ownership/lineage, status styling. Renders natively on GitHub/Markdown
- JSON output: add `--json`
- Optional executable isolation: `--check-isolation --root <repository>` executes trusted project commands for `standalone_harness` and `provided_mocks[capability].contract_suite` twice (real and mock). All non-external components in the supplied scope require a harness and a provided mock for every capability. Required-capability `fakes` paths must exist. It does not sandbox code or establish that a suite is comprehensive. See [`COMPONENT-ISOLATION.md`](../COMPONENT-ISOLATION.md) and `examples/components/`.
- Binding generation: `--bind [SUBJECT…] --revision REV --root R [--include GLOB…]` prints `subject_bindings` entries (the provider component's tracked `source_paths` files from `git ls-files`, hashed) then, as `#` comments (so the whole output can be pasted), the refreshed digests for those subjects' evidence to apply by hand: a record's own `artifacts`, and a `runs` entry's `artifacts` once (records inherit them, so they are not repeated per record); `--json` returns them as `evidence_artifacts` and `run_artifacts`; it refuses unless the files equal `REV`. Workflow: [`BROWNFIELD.md`](../BROWNFIELD.md) § Keeping a bound spec current.
- `--check-artifacts --check-test-names`: a `test` evidence provenance `<file>::<name>` must find its last segment (minus a `[params]` suffix) in the existing file as a whole identifier, and any module segments before it declared in order (`mod X` in `.rs`, `class X` in `.py`, else as identifiers) (textual, language-neutral; opt-in because nested or generated test names can differ).
- SHA-256 values must be quoted in YAML: an unquoted all-digit digest (a drafting placeholder such as 64 zeros) parses as a number and is rejected with a targeted error rather than coerced.
- Runs (`runs`, `Evidence.run`): records from one verification run name it and inherit the run's unset `subject_revision`, `subject_version`, `artifacts`, `timestamp`, `verifier` and `environment` on load (instead of YAML anchors); `REF-15` rejects an unknown run.
- Measured evidence: a `{id, text, threshold: {metric, op, value, unit}}` criterion plus `Evidence.measurements: {metric: value}`; `EV-09` rejects passing evidence that lacks the metric or violates the bound, and contradictory failing evidence; `--evidence-report` lists `measurements`.
- Optional local artifact integrity: `--check-artifacts --root <repository>` checks declared source/schema paths and source/evidence SHA-256 hashes without executing or fetching artifacts; a `subject_bindings` hash mismatch names the stale subject, requirements and evidence (`stale` with `--json`). An explicit root is required; ordinary validation remains metadata-only. A check run that validates a stage (`--stage` or `--compat`) also prints the stage's reports (acceptance, formal gaps and the other `note:` lines; `acceptance`, `formal_*` and the rest with `--json`), so the git check enabled by `--root` is not dropped.
- Delivery plan: `--plan <id>` prints provider-first waves of affected components (parallelizable within a wave) with each one's `requires`, `fakes`, `source_paths`, `test_paths`, plus requirements and evidence to revisit; built on `--impact`.
- Acceptance: optional `system.acceptance` (`stage`, `accepted_by`, `accepted_on`, `revision`, `scope`, `notes`) records the human decision, separate from a passing stage. Every run reports it (`acceptance` in `--json`, `note:` lines) with whether that stage passes now and whether it may be stale (evidence dated after `accepted_on`, `subject_bindings` at another revision; with `--root` in a git checkout also an unknown or non-ancestor `revision` and `changed_since_acceptance`, the commits since it touching a component's `source_paths` or, after the later of `revision` and the newest commit that changed any `acceptance` field, the spec, naming the components; `code_checked` is false and a note says so without `--root` or git; quote an all-digit `revision`); the `status` docs block shows it when recorded.
- Formal assessment: `Component.formal_assessment` (`applies`, `indicators`, `rationale`, `evidence`, `risk`; `COMP-12` checks it is consistent; at `release`, `COMP-13` refuses an applicable component with no passing `model-check`/`proof` evidence unless `risk` names an accepted risk on it) records the constitution's per-component assessment; `--stage verification`/`release` list components with none (`formal_unassessed`) and applicable ones without a passing `model-check` or `proof` record (`formal_no_evidence`, minus gaps accepted by `risk`, listed apart as `formal_accepted_gaps`; a record the assessment cites counts even when it verifies another component's requirement, like a shared protocol model) as `note:` lines and in `--json`.
- Evidence report: `--evidence-report` (YAML, or `--json`) prints, per active requirement version, `verified`, `failing`, `uncovered`, `records`, `blanket` (records without `criteria`), `skipped`, `methods`, `model_only` (every passing record is a `model-check` or `proof`: the model is not tied to the implementation by a test), `holder` and `priority`, from the same evaluation the release stage uses.
- Release scope: `system.release_scope` or `--release-scope P0[,P1]` defers active requirements whose `priority` is set and out of scope; release obligations skip them, the entities they target and the components providing those, and the output lists them (`deferred`). In-scope requirements depending on or refined by deferred unverified ones still fail.
- Criteria and holders: a criterion may be `{id, text}` (`REQ-10`); evidence and handoff results name it by ID or text. `Requirement.holder` with `system.evidence_methods` restricts evidence methods (`EV-07`); `system.evidence_policy.require_criteria` makes blanket records an error (`EV-08`) and stops them covering the whole requirement.
- Handoff scope: `--check-scope <component> --changed <file|-> [--allow <path>]...` reads changed paths (one per line, e.g. `git diff --name-only`) and reports any outside the component's `source_paths`, file `test_paths`, file `fakes` and owned `schema_path`s. Path comparison only; no filesystem access.
- Docs rendering: `--render-docs FILE… [--check]` rewrites each `<!-- system-spec: KIND -->` … `<!-- /system-spec -->` block from the model (kinds: `components`, `capabilities`, `contracts`, `data-models`, `contracts` (each failure mode with its `interface.errors` entry, `mode → error`), `layers`, `domains` (declared order, with their internal components), `requirements` (with status, `proposed` and `applies_to`), `evidence` (one row per record), `status` (summary counts), `risks` (with description, owner and waiver until its expiry; `report:risks` stays compact), `evidence-summary`, `report:risks|coverage`, `diagram:components|hierarchy|risks|runtime`); a block may select its own spec with `<!-- system-spec: KIND spec=PATH -->` (path relative to the Markdown file; loaded and structurally validated once per run), for documents covering a spec and its imports; a marker counts only when its HTML comment stands alone on its line outside fenced code (inline mentions and fenced examples are plain text), and an unclosed block, a marker inside a block or a stray closing marker is an error naming the line, with nothing written; text outside markers is untouched, CRLF files stay CRLF, `|` and newlines in cells are escaped, output is idempotent, `--check` writes nothing and exits non-zero when a file would change. With `--root` in a git checkout the `status` block's acceptance rows run the same git check as validation (`Acceptance current` is `yes`, or `no: …` naming an unknown or non-ancestor revision or `changed since acceptance: <components>`, never commit hashes or counts, so the committed row survives a squash or rebase merge; the validation `note:` keeps them), so `--check` also fails once code changes after the accepted revision; without it the row reads `yes (code not checked)`.
- Evidence citing a test file (`tests/kv.rs`) or a runner selector from `test_paths` (`nextest::-p store`) matches the reported tests under it: by file (`file` property or attribute, `<file>::` prefix of `test`, or a `--test-map` entry's `test`), or by report-ID prefix (`store::` for nextest `-p store`; other selectors via `--selector-prefix SELECTOR=PREFIX`). It is present when any test matches and agrees when all of them passed and any binding is the record's requirement.
- Test reports: `--check-report <junit.xml>...` requires each test case to carry one `verifies` property (`<requirement>@<version>`; optional `test` property gives the evidence provenance, default `classname::name`) and `test` evidence to agree with the reports; `--test-glob <pattern>` (repeatable, with `--root`) also requires every file under a component's `test_paths` whose name matches a pattern (`test_*.py`, `*.test.ts`, `*_test.go`) to have at least one reported test, so tests that never run cannot escape the binding check; `--test-pattern <regex>` (repeatable, with `--root`) does the same by file content, matched per line, for languages whose tests live in ordinary source files (Rust `^\s*#\[(?:\w+::)*(?:test|rstest)\b`, Go `^func Test`); a test's file is its `file` property or attribute, else the `<file>::` prefix of its `test` property, and selector `test_paths` are skipped. `--test-map <file>` (YAML/JSON, report test ID → `<requirement>@<version>`, or `{verifies, test}` where `test` is the provenance evidence cites, for runners like cargo-nextest whose JUnit IDs are `<binary-id>::<name>`) binds tests as if they carried `verifies` (and `test`), for both commands; `--report-scope evidence` checks only tests named by `test` evidence (or under a cited file or selector) for presence and result against the evidence's own binding (a test may have no binding or several, but any it has must include the record's requirement) and counts the rest, grouped by owning component (the most specific `source_paths`/`test_paths` entry containing the test's file, else a selector's report-ID prefix, else `(unowned)`) in the output and as `unbound_by_component` with `--json`, per file with `--verbose` (`unbound_files`); `--max-unbound N` fails when more than N tests owned by internal components are unbound (a ratchet while requirements are written; `(unowned)` and external-component tests are listed, marked, and not counted, so two specs checking one shared report each hold their own count; `--json` has `unbound_owned_tests` and `unbound_not_counted`); `--test-map` `verifies` may be a list; `--emit-test-map <junit.xml>... --cargo-metadata <meta.json>` (`cargo metadata --format-version 1 --no-deps`) prints a `--test-map` for cargo-nextest reports: each test's `<file>::<name>` (binary ID → target source file, then `mod` declarations along the module path, `#[path]` followed; the file's own modules are dropped: `src/store.rs::tests::round_trips`) and `verifies` from evidence citing the file, the exact test or a `nextest::-p PKG` selector; one `--cargo-metadata` per `--emit-test-map`, in order, paths relative to `--root` (default `.`); unresolved tests are listed on stderr; `--emit-evidence` yields a record per binding (`unbound_tests` with `--json`, a `note:` line otherwise). `--emit-evidence <junit.xml>...` prints the derived `test` Evidence records (add `subject_revision` and `verifier` for `EV-04`). pytest: `reference-implementation/conftest.py` shows a `verifies` marker feeding both properties
- Experiences (optional, [`EXPERIENCE.md`](../EXPERIENCE.md)): `views` and `experiences` are validated by `EXP-01`..`EXP-12` only when declared; `--check-artifacts` checks `VisualReference` files and hashes. `--impact`, `--context` and `--diagram` do not include them yet
- Handoff return: `--check-return <file> [--allow <path>]...` checks an implementer's return (`component`, `results`, `unmet`, `changed`, `findings`; schema `handoff-return.schema.json`, `--return-schema`) against the spec: every active requirement targeting the component (or a capability it provides or data model it owns) is a result or unmet, result versions are current, passing results have no skipped checks, results may cover single criteria (`criteria`) and together must cover every criterion of a requirement unless it is listed unmet, test provenance is under `test_paths`, failing results are listed unmet, changed paths stay in scope. Findings are echoed in `--json` output.
- Cross-spec references & hierarchy: `system.imports` pins another system's spec (`path`, `version`, `capabilities: {id: version}`, optional `sha256`); an `external` component provides `<import-id>:<capability>` and consumers require it as `<import-id>:<capability>@^1.0`, so contracts are not copied (`IMP-01`). `system.exports` optionally lists which capabilities a spec exposes (omitting exports all). A component with `realized_by: <import-id>` is a black-box subsystem realized by a child spec: `--check-imports --root <repository> [--import-path ID=FILE]` (`--import-path` or a vendored `imports/<id>.yaml` next to the spec replaces a missing sibling checkout or a `path` outside the root, and messages name the file actually read; the pin's `sha256` still verifies) verifies system/capability pins, `sha256`, `exports`, contract inclusion (`child.provides ⊇ component.provides`, `child.external_requires ⊆ component.requires`, capability/data compatibility), cross-spec requirements (`<import-id>:<requirement-id>` in `depends_on`/`refines`), and release maturity for verified in-scope components. With `mode: baseline` the import is a requirements baseline: `--check-imports` also checks `artifacts` digests and compares requirements, risks, views, experiences and state sets, reporting changes or removals not covered by `refinements` (`allow_fields`, `id_prefix` for systematic changes) and refinements that name no deviation; additions pass.
- Workspaces: `<workspace.yaml> --workspace [--stage S]` validates every member of a super-repo manifest (`members`: `id`, `path`, optional `link`, optional `stage` override) at `S` (default `release`), runs each member's import check against the workspace root, and checks that imports target members with agreeing `link`s, system IDs are unique and imports are acyclic. Offline; see [`WORKSPACE.md`](../WORKSPACE.md).
- System-wide requirements: `applies_to: {kind: capability, has_interface: true}` on a system-targeted requirement needs evidence per selected entity (`subject_id`); `--evidence-report` shows `applies_to` and the uncovered entities.
- Proposed requirements: `proposed: true` (with `status: specified`) passes the stages, is listed under `proposed` in the output and is deferred at release like an out-of-scope priority.
- Overviews: `--diagram hierarchy` (system, domain, component, capability and data model with requirement counts), `--diagram risks` (risk, target, mitigating requirements), `--diagram runtime` (flow by domain, edges labelled with `interface.operation`, caller → provider, `async` dashed, `via` through the mediator; `via` on a `publish: true` interface drawn publisher → mediator → subscriber), `--report risks` and `--report coverage` (Markdown tables per owning component, with capabilities and data models rolled up, by category, priority and mandatory under headings, single-valued breakdowns omitted, with totals; `--json` prints the data). All output is sorted by ID.
- Exporters: `--export backstage [--owner TEAM]` prints Backstage catalog entities (System, Component, API, Resource; multi-document YAML) and `--export structurizr` prints a Structurizr DSL workspace (components as containers, `external` ones as external software systems, resolved requirements as relationships). Backstage requires an owner that the metamodel does not model, hence `--owner` (default `unknown`). Lifecycle maps `verified`→`production`, `draft`/`specified`→`experimental`, `deprecated`→`deprecated`; API types are `openapi`/`asyncapi`/`other` from the interface. One-way, lossy exports; the spec stays the source of truth.
- Optional drift check: `--check-drift --root <repository> [--deps FILE]` (`--deps`: language-neutral graph, YAML/JSON `packages: [{name, path}]`, `edges: [{from, to, kind: normal|dev|build}]`, e.g. generated from `cargo metadata` or `go list`; packages map to components by path, `normal`/`build` edges need a `requires` or `bindings` capability, `dev` edges also pass through `test_requires`, unowned packages are `unchecked`; `--check-ownership` makes a package owned by no or several internal components (by `source_paths`; `test_paths` confer no ownership, and the error says when a package appears only there) an error instead — the packages are the `--deps` ones plus every Cargo.toml `[package]` and named package.json under `--root` (not `target`, `node_modules`, `.git`, venvs) — and (the scan reads the files git tracks or leaves unignored under `--root`, else all but hidden, `target*`, `node_modules` and venv directories, so build output is never a package; `--test-pattern` and `--test-glob` read test files the same way) `--ownership-spec FILE`, repeatable, adds the other specs describing the same repository (a package is owned when a component of any given spec owns it, an error when components of two specs, or one, do; components are named `spec:id`), and a component's `source_paths` entry inside a package that another component owns (in this spec or a given one) is an error as overlapping ownership, and one inside a package `--ownership-ignore` exempts is a claim on an ignored package (an exempted root package, `.`, covers only its own directory, so a plain directory like `models/` can still be owned); `--ownership-ignore GLOB`, repeatable, exempts spikes and fixtures by path or name, e.g. `'crates/*-spike'`) parses Python sources and tests under `source_paths` and `test_paths` (never executes them), and scans JS/TS files (`.ts .tsx .js .jsx .mjs .cjs`) for `import`/`export … from`/`require()`/`import()` specifiers (regex over comment-stripped text; relative specifiers and workspace package names from `package.json` are followed, `node_modules` is skipped) and reports an import between components with no `requires` capability or `bindings` entry reaching the imported component, and JSON Schema top-level `properties` that differ from `DataModel.fields`. It also reads `Cargo.toml` manifests under `source_paths` (parse only): `path` dependencies (including `workspace = true` ones resolved from the root `[workspace.dependencies]`) that reach another component need a matching `requires`/`bindings` entry, and `dev-dependencies` on another component are rejected like test imports unless the same dependency is already a normal/build dependency (the same link, already checked against `requires`). Unsupported schema formats, test selectors, components without `source_paths`, external components' own sources, `via` edges and in-root import/path-dependency targets owned by no component (`unchecked: <component>: '<target>' not owned by any component`) are listed as `unchecked`. With `test_scope: integration`, test dependencies on providers of `requires` or `test_requires` capabilities are allowed.
- Run tests: `uv run pytest` (incl. `corpus.yaml`: one or more invalid patches of `example.yaml` per invariant ID; examples are the valid corpus)
- Docker: `docker build -t metamodel . && docker run --rm metamodel [python metamodel.py ... | pytest]`
- CI & remote: `.github/workflows/metamodel.yml` runs `pytest` automatically on `push`/`pull_request` and runs either script in Docker when dispatched manually (`script`, `args`)

## Validator Behavior

- **Schema**: unknown fields are rejected (`extra="forbid"`); `status` defaults to `draft`.
- **Invariants**: `INVARIANTS` maps each ID (spec.md § 11) to its stage, waiver kind and rule; errors are prefixed `[ID]`, and a test keeps the table in sync with spec.md.
- **Stages** (`--stage`): each invariant runs at its stage and later.
- **Waivers**: valid below `release` when `treatment` is `mitigation`/`acceptance`, `mitigated_by` is non-empty and `expires` (date or stage) is not passed (stage expiry: current stage after `expires`). `Risk.waives` accepts either the waiver kind or its invariant ID (`DATA-03`, `COMP-03`, `COMP-05`, `COMP-06`, `REQ-01`). Active waivers are listed as `waivers` in `--json` output.
- **Interfaces**: capabilities required by another component need `interface`; `operation`, `idempotent` and `auth` must be defined; `request`/`response` must name data models; `errors` keys must equal `failure_modes`.
- **Requirements**: `deprecated` requirements are inactive (no coverage, conflicts or evidence obligations); `Requirement.kind` must match its `category` (`REQ-07`); a conflict is resolved when either side's `resolved_by` names an active requirement; mandatory, mitigating, resolving and declassifying requirements need evidence and verified dependencies at `release`; `declassified_by` relaxes classification propagation only when it names an active requirement.
- **Component tests** (`COMP-08`): when a component declares `test_paths`, `test`-method evidence for it (subject is the component, a capability it provides, or a data model it owns) must have a `provenance` file part (before `::`) under one of them, or match a selector entry (`tool::selector`, exact or continued with `::`). Opt-in; components without `test_paths` are unchecked. `--check-drift` scans tests like source, and additionally rejects any test import of another component (declared or not): tests use the fakes.
- **Fakes** (`COMP-09`): a component that declares `test_paths` needs a `fakes` entry for each required capability, located under `test_paths` (file or selector), unless `test_scope: integration`; entries for capabilities it does not require are errors. `--check-artifacts` verifies the files exist. `COMP-10` (release): a capability that any component fakes needs an active `contract`-category requirement with valid evidence, so provider contract tests back the fake; fidelity of the fake to those tests is not checked.
- **Layers**: dependencies allowed within a layer or toward any lower layer (incl. non-adjacent); with non-empty `system.layers`, every component must declare one. Adjacency and source-code dependency rules need separate verification.
- **External components** (`COMP-11`): `external: true` declares no `layer`, `domain`, `requires`, `test_paths` or `fakes`, and is exempt from `COMP-02`, `COMP-03` and `DOM-01`; `--diagram` draws it as a hexagon outside the system listing its API. `via` maps a required capability to another required capability mediating it at runtime (`REF-05`); `--diagram` dashes such edges.
- **Domains**: optional and orthogonal to layers; with non-empty `system.domains`, every component must declare one (`DOM-01`). A dependency between components of different domains needs the target in the consumer domain's `uses` (`DOM-02`); `uses` is acyclic (`DOM-03`). Same-layer siblings that must stay independent are domains without `uses` between them. `--diagram` nests domain subgraphs inside layers.
- **Resolution**: excludes the consuming component; rejects ambiguous providers without a binding, dependency cycles, and active components requiring deprecated capabilities (`COMP-07`); one version per capability ID.
- **Versions** (`_ver_ok`): dot-separated integers; equal major, remaining segments ≥ minimum; non-numeric never matches. No segment normalization, major-zero rules, prereleases or general ranges.
- **Risks**: mitigating requirements need valid evidence; `avoidance` also needs verified `mitigated_by` and no `residual_accepted`; `acceptance` and `transfer` need `residual_accepted: true`, and `transfer` needs `transferred_to`. Accepted residual risks are listed as `residual_risks` in `--json` output. Mitigation effectiveness is not checked.
- **Classification**: missing classification is `unknown`; inventory requires an active `classification_review` requirement. Unknown classifications block architecture and later stages, including when lineage is declassified (`DATA-05`, `DATA-06`). Existing inputs that omitted classification must now state a reviewed value or an inventory review obligation.
- **Evidence**: requires a passing, unskipped record for `(requirement_id, requirement_version)`; rejects unsuperseded failures. `model-check` requires `bounds`; `subject_id` must resolve. At release, `timestamp` and `verifier` are required. Explicit `subject_version` / `subject_revision` pairs match `subject_bindings` and current modeled versions (`EV-04`); legacy version-valued `subject_revision` remains supported when no binding/pair is declared. Skips block release (`EV-05`). Optional `artifacts` hashes verify local file integrity only; criterion coverage, Git authenticity and build correspondence remain review obligations.
- **Evidence criteria** (`EV-06`, `REQ-04`/`REQ-05`): `Evidence.criteria` lists the requirement criteria a record covers (exact strings; empty = whole requirement). Per-test or per-group records can then verify a requirement criterion by criterion: it is verified only when every non-superseded record passes and every criterion is covered by a passing record (or one whole-requirement record). `REQ-04`/`REQ-05` name the failing or uncovered criteria. A failing criterion still blocks release; criteria make it attributable, not waivable.
- **Compatibility** (`check_compatibility`, `check_data_compatibility`, `--compat`): compares clauses as string sets; reports added preconditions, removed postconditions/invariants, added failure modes, capabilities removed without prior `status: deprecated`, removed data models, data models with removed fields, changed field types or classification, and missing major bumps. No clause semantics, interface or constraint comparison.
- **Context** (`--context`): the component, its provided/required capabilities, owned and interface data models, applicable source bindings, and requirements/risks targeting them or the system; evidence excluded.
- **Impact** (`impact_analysis`, `--impact`): follows capability, ownership and lineage dependencies transitively; reports affected components, capabilities, data models, requirements (incl. system-level and dependent), evidence (by requirement or `subject_id`; for `applies_to` requirements only the reached subjects) and `tests` (test paths and selectors of affected components); `--impact-paths` first maps changed files to components. Stored evidence is not changed.

## Limitations

- `consistency` and `quality_attributes` parsed only. Source/schema paths are checked for existence/containment with `--check-artifacts`; `--check-drift` covers Python imports, JS/TS relative and workspace-package imports (not tsconfig `paths` aliases, bundler aliases or computed specifiers), Cargo `path`/`workspace` dependencies and JSON Schema property names only (no other languages or formats, registry or `target.*` Cargo dependencies, field types, `required`, `$ref`/`$defs`).
- Schema additions are backward compatible for specs (new fields are optional) but not forward compatible for tools: a validator older than a field rejects specs that use it (`extra="forbid"`), e.g. `test_paths` requires a validator that includes it.
- No automatic evidence invalidation; impact analysis only reports it.
- Results separate schema from metadata errors; metadata errors carry invariant IDs but not stage labels.
- JSON Schema does not encode all invariants.
- Example test and benchmark provenance values are illustrative; sample formal models are supplied in [`../examples/greenfield/Inventory.tla`](../examples/greenfield/Inventory.tla), [`Inventory.cfg`](../examples/greenfield/Inventory.cfg), [`Inventory.als`](../examples/greenfield/Inventory.als) and [`metamodel.als`](metamodel.als).
- `VALID` means only that implemented checks found no errors; passing tests establish only the behavior they cover.
