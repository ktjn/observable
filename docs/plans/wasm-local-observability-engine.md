# Feature plan: WASM-native local observability engine

**Status:** Phases 1-2 complete. Phase 3 (self-instrumentation) not started.
**ADR:** [ADR-047](../../spec/adr/ADR-047-wasm-local-observability-engine.md).
**Owner:** `observable-web` (frontend) + `libs/query-core` (shared Rust/WASM).
**Scope:** Collapse the frontend's dual HTTP/playground runtime into one transport-parameterized runtime; make the local engine durable, tenant-aware, and alert/health-capable; ship it as an embeddable per-site module. No browser extension.

## 1. Baseline (verified on main)

- `apps/frontend/src/runtime/httpRuntime.ts` and `playgroundRuntime.ts`: two independently composed `RuntimeApi` objects.
- `apps/frontend/src/api/*.ts` (e.g. `logs.ts:42,69,90,103`): each function calls `fetch()` directly with a hand-written URL; no shared route table.
- `apps/frontend/src/playground/engineWorker.ts`: `executeLogsSearch`/`executeLogsTail`/`executeLogsContext` (~lines 631-663) build ad hoc SQL — no facets, no total count, no tenant bind — vs. `services/query-api/src/logs.rs::search_logs` (lines 39-150), which binds `ctx.tenant_id` on every count/facet/data query.
- `apps/frontend/src/playground/duckdbStorageWriter.ts`: flat, unscoped tables; no tiering (ADR-012), no durability.
- `apps/frontend/src/playground/engineWorker.ts:23-29`: the `logs` table does store a `tenant_id` column (written as `DEMO_TENANT_ID` on insert) — but until this slice no read query bound it, nor any of `severity`/`from`/`to`, and `total`/`facets` were hardcoded stand-ins rather than real counts.
- `libs/query-core/src/service_query.rs::service_summary_from_row` (~lines 760-771): hardcodes `slo_breaching: false, active_alert_count: 0, latest_deployment: None`; the real values only come from `apply_catalog_enrichment` in `services/query-api/src/discovery.rs` (lines 640-753), never called from the playground engine.
- `apps/frontend/src/runtime/playgroundViewSubscriptions.ts`: faithfully implements `ViewSubscriptionTransport` (snapshot/delta/replace/invalidate/reset, revisions, `supersedesThrough`) — already matches ADR-046.
- `apps/frontend/src/playground/liveTick.ts` / `engineWorker.ts:500-502`: independent 3s-interval direct-storage mutation, disconnected from the above transport.
- `libs/query-core`: precedent for Rust logic compiled to both native and WASM targets (the comment at `libs/playground-wasm/src/lib.rs:297-300` confirms bucket/summary math is "the same pure computation ... reused here verbatim").

## 2. Phase 1 — Transport collapse (foundation, blocks everything else)

- Define a shared route table: `{ method, path }` keyed entries matching the real REST paths in `spec/09-api.md`, one entry per existing `api/*.ts` function.
- Add a `RequestTransport` interface: `dispatch(route, params, body) -> Promise<unknown>`. Two implementations:
  - `httpTransport`: performs the existing `fetch()` call.
  - `wasmTransport`: dispatches into the WASM engine using the same `{method, path}` key — an in-process call, not a `fetch()` interception (keeps it outside any future fetch auto-instrumentation, ADR-048).
- Rewrite `api/*.ts` functions to call `dispatch(route, ...)` instead of `fetch()` directly.
- Replace `httpRuntime.ts`/`playgroundRuntime.ts` with one `createRuntime(transport)` factory. Mode is chosen once at boot (strict — no mixing, per ADR-047 §1).
- Exit criteria: `runtime.contract.test.ts` (existing contract test) passes against both transports unmodified; `httpRuntime.ts`/`playgroundRuntime.ts` as separate files are deleted.

## 3. Phase 2 — Close the identified gaps

- `wasmTransport`'s log handlers call the same shared query path `search_logs` semantics expect (facets, total count, tenant bind) instead of the ad hoc SQL in `engineWorker.ts`. **Done**: `DuckDbLogQueryApi.search()` now accepts `tenantId`/`spanId`/`severity`/`from`/`to`/`facets`, binds them all into a shared `WHERE` clause (mirroring `log_search_where_clause` in `libs/query-core/src/planner.rs`), and runs a real `count()` query plus one facet query per requested field (allowed set mirrors `requested_log_facets`: `service_name`, `severity_number`, `environment`, `host_id`) instead of returning hardcoded `total`/`facets` stand-ins. `engineWorker.ts`/`engineClient.ts`/`wasmTransport.ts` thread the new params and real result through.
- Thread tenant binding through every local query, even though a local instance has one implicit tenant (ADR-047 §5). **Done** for `/v1/logs` as part of the above (the `logs` table already had `tenant_id` stored; it just wasn't bound on read). Other routes' tenant binding is unchanged by this slice.
- `duckdbStorageWriter.ts` moves from in-memory DuckDB to OPFS/IndexedDB-backed persistence. **Done**: `duckdbStorageWriter.ts` itself needed no change (it only formats `INSERT` SQL against whatever connection it's given) — the actual seam was `initEngine()` in `engineWorker.ts`, which now opens the DuckDB-WASM database against `opfs://observable-playground.db` (falling back to in-memory if OPFS is unavailable), uses `CREATE TABLE IF NOT EXISTS`, and only reseeds when the `spans` table is empty (loading `seededSeries` from the persisted `metric_series` table otherwise, since live-tick modulation needs it). "Reset playground" is unaffected — it already does an explicit `DELETE FROM *` + reseed. Verified empirically via a new Playwright e2e test (`e2e/playground/durability.spec.ts`): reset to a fresh random seed, reload the page, confirm the same (not re-seeded) dataset is still shown — this test was confirmed to fail without the fix and pass with it.
- Extend the shared Rust crate(s) so `alert-evaluator`'s real evaluation logic compiles to WASM; `service_summary_from_row` calls it instead of hardcoding `slo_breaching`/`active_alert_count`. Scoping correction: no `observable-health` crate exists in this repo (only `services/alert-evaluator`); the real `slo_breaching`/`active_alert_count` enrichment is a live Postgres-backed HTTP call (`alert-evaluator`'s `/internal/alerting-enrichment`), not a pure function — only `evaluator.rs::calculate_burn_rate`/`evaluate_burn_rate` are pure/WASM-portable. Split into two sub-slices per this finding:
  - **Sub-slice A — seed SLO definitions (Done)**: `libs/playground-wasm/src/generator.rs::generate_slo_definitions` generates one availability SLO per topology service (canonical SRE burn-rate thresholds: 14.4x fast / 6.0x slow against a 28-day window), exposed via `generate_slo_definitions_json` (wasm-bindgen) and seeded into a new local `slo_definitions` table in `engineWorker.ts` (seeded independently of the spans-table emptiness check, so an OPFS-persisted database from before this table existed still gets it). No separate `alert_rules` table — the playground has at most one burn-rate rule per SLO, so thresholds live on the SLO row itself. Found and fixed a real regression while verifying this empirically via e2e: OPFS-backed storage (from the prior durability slice) persists across separate Playwright invocations (confirmed: `observable-playground.db`/`.db.wal` survive even a fresh `npx playwright test` process), so a completed "Reset playground" in one run bleeds into the next. Added `e2e/playground/clear-opfs-storage.ts` as Playwright `globalSetup` (clears OPFS before each suite run) and had `durability.spec.ts` clean up its own OPFS mutation afterward — both via navigating to a static asset instead of the SPA, since the live engine holds an OPFS lock that blocks `removeEntry` otherwise.
  - **Sub-slice B — wire real burn-rate evaluation (Done)**: `calculate_burn_rate`/`evaluate_burn_rate` (and `EvalResult`/`SloBurnRateCondition`) moved verbatim from `services/alert-evaluator/src/evaluator.rs` into a new `libs/query-core/src/slo_evaluation.rs` module; `alert-evaluator` now depends on `query-core` and imports them from there instead of defining them locally (its own call sites/tests unchanged beyond the import). `service_summary_from_row` (the playground's copy in `query-core::service_query`) takes an `Option<&SloBurnRateRow>` and runs the real evaluation against it when a service has a seeded SLO. `engineWorker.ts::computeSloBurnRateRows` computes bad/total span counts over fixed fast (60min)/slow (360min) windows matching the seeded thresholds and joins them with `slo_definitions` before calling the now-3-arg `compute_service_summaries` WASM binding. `active_alert_count` is approximated as `1` while breaching, `0` otherwise (no local firing-state store to count against — confirmed with the user before implementing). Verified via a new e2e test (`e2e/playground/slo-evaluation.spec.ts`): `payment` (generator's highest fixed error weight, 0.15) shows "Breaching", `web` (0.04) shows "Meeting commitments" — real evaluation, not the previous hardcoded `false`.
- Rewire `liveTick.ts` to emit through `ViewSubscriptionEvent`s (the existing `playgroundViewSubscriptions.ts` transport) instead of mutating storage directly; delete the direct-mutation path once callers only observe it through events. **Done**: `engineWorker.ts` posts a `LiveTickNotification` (`buildLiveTickNotification`, unit-tested) after each tick; `engineClient.ts` exposes `onLiveTick`; `playgroundViewSubscriptions.ts` bridges it into `replace`/`delta` events for subscribed `telemetry-watermark`/`log-tail` views (unscoped, matching the real broker's empty-`services` fallback). Still writes to DuckDB directly — that storage write itself isn't going away, only silent-polling discovery of it is. Not covered by vitest: the `engineWorker.ts`/`engineClient.ts` Worker wiring itself (no `Worker` in jsdom, consistent with this boundary's existing untested status) — verify via `apps/frontend/e2e/playground/readonly-view-subscriptions.spec.ts` / `logs.spec.ts` against a real browser before relying on this in production.
- Exit criteria: playground-mode service summaries reflect real (locally evaluated) alert/health state — **met**; a page reload after a browser restart still shows prior local data — met (durability sub-slice); `liveTick`-driven updates are observable only via `ViewSubscriptionEvent`s in tests — met (liveTick slice). Phase 2 complete.

## 4. Phase 3 — Self-instrumentation

- The engine emits its own logs/traces/metrics (ingestion latency, query cost, sync events) through its own query/storage path, into a local tenant equivalent to the real `system`/`platform` tenant (`spec/17-self-observability.md` §2.1).
- Exit criteria: a local "system" view exists and is queryable the same way any other tenant's data is.

## 5. Phase 4 — Embeddable delivery

- Package the engine (Phase 1-3 behavior) as a module a site includes directly — no browser extension, no host permissions.
- Any instrumentation of the embedding site reuses the real OTel Browser SDK packages (shared decision with ADR-048), not a hand-rolled equivalent.
- Exit criteria: a sample site under the operator's control, with no backend, runs the full Observable UI against `wasmTransport` only, with durable storage across a browser restart.

## 6. Deferred (not in this plan)

- Cross-site aggregation across multiple embedded instances. If taken up later: WebRTC for the data path, manual/local (no-server) signaling for same-machine peers only — not a signaling server, not a browser extension. Revisit only if per-site isolation proves insufficient in practice.
- Mixed per-route transport selection (ADR-047 explicitly rejects this).
